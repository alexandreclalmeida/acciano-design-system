# ADR 012 — Elevação como tokens

**Date:** 2025  
**Status:** Accepted

## Context

Several components use `box-shadow` to convey elevation — the perception of depth relative to the surface. Values like `0 1px 2px rgba(0,0,0,0.08)` were initially hardcoded in component CSS, creating inconsistency and making system-wide adjustments difficult.

The main options considered were:

- **Hardcoded `box-shadow` values per component** — each component defines its own shadow
- **Elevation as CSS custom properties** — named tokens consumed by components
- **Elevation via a utility class** — a shared class applied to components that need elevation

## Decision

Define **elevation as CSS custom properties** (`--elevation-sunken`, `--elevation-raised`, `--elevation-overlay`) generated by Style Dictionary from a dedicated `Elevation.tokens.json` source file.

## Rationale

- **Consistency:** All components that share the same elevation level use the same token. A change to `--elevation-raised` propagates everywhere automatically.
- **Semantic naming:** `sunken`, `raised`, and `overlay` describe the intended depth relationship, not the specific shadow values. This makes component code more readable and intent-driven.
- **Aligns with the Figma source:** The `Foundations / Elevation` page in Figma defines exactly these three levels. The token names mirror the design language.
- **Utility classes were ruled out:** They would require adding a class to component markup, mixing visual concerns into the HTML structure. CSS custom properties keep the elevation intent in the stylesheet where it belongs.

## Consequences

- Style Dictionary generates `dist/elevation.css` with the three elevation tokens.
- Components reference `var(--elevation-raised)` or `var(--elevation-sunken)` in their CSS modules — never raw `box-shadow` values.
- `transparent` shadows (used in the sunken token) are intentional keyword values, not placeholders.
